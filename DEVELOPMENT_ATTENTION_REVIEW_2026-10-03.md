# W&B application — areas needing attention

Date: 3 October 2026. Basis: ../DEVELOPMENT_PROCESS.md, current active source, existing improvement register and handover. This is a source/document review, not a new browser trial, regression run or independent aircraft validation. No application behaviour was changed.

Apply Understand → Explore → Decide → Execute → Verify → Learn. Priorities below recommend sequencing; candidate solutions are not approved implementation requirements. Existing PRO IDs refer to PROFESSIONALIZATION_IMPROVEMENT_REGISTER.md.

## 1. Reproducible verification — high priority

**Classification:** confirmed development-process gap (PRO-01/02).

**Problem:** The next maintainer cannot reliably reproduce the suite from the application folder. Current browser tests still import a user-specific Playwright installation; no package manifest, lockfile or CI workflow was found in the non-Archive project inventory. The offline test also relies on a historical Git fixture, as documented in the handover.

**Evidence:** tests/dev-scope.test.cjs:3; tests/mission-accounting.test.cjs:4; tests/responsive-review.cjs:2; DEVELOPMENT_HANDOVER_2026-10-01.md, verification section.

**Next stage:** Decide the smallest portable test arrangement and documented fixture policy. A local release gate is a viable first step before hosted CI.

**Acceptance:** A second environment runs one documented command against an identified app/configuration candidate, returns failure for failed checks, and retains useful diagnostics. Historical passing counts are not current release evidence.

## 2. Aircraft data and independent calculation evidence — high priority

**Classification:** data/assurance requirement; no arithmetic defect established (PRO-03/04).

**Problem:** Correct arithmetic needs verified aircraft inputs and an independent reference. Delivered-aircraft fit, weighing inclusion and exact source locators remain outstanding in the handover. Current rack records cite RFM positions supplied by the user, rather than a complete document/revision/locator chain.

**Evidence:** config.js:908 and subsequent rack definitions; handover, outstanding work; FUTURE_USER_TECHNICAL_MANUAL.md, technical substantiation and release checklist.

**Next stage:** Understand and inventory unresolved source values; assemble a field-to-source matrix and independently derived expected calculations. Preserve settled accounting decisions unless new evidence contradicts them.

**Acceptance:** Significant masses, arms, limits, fuel rules and baseline assumptions have provenance and disposition. Reviewed examples cover nominal loads, signed adjustments, partial racks, patients, fuel transitions and envelope boundaries. Independent expected values must not be generated by the engine being tested.

## 3. Editor deletion, retirement and hidden dependencies — high priority

**Classification:** observed coverage gap and design discovery; operational failure still requires reproduction (PRO-07/08/15).

**Problem:** Editable catalogue IDs participate in relationships beyond role membership. Mission-item deletion checks selected mission use and removes preset references, but does not explicitly inspect other items' carrier defaults or extra-crew mappings. Role-fit deletion checks named-stowage links but does not explicitly check all mission carrier references or accepted-session dependencies before deletion. Extra-crew choices build specific catalogue IDs in code.

**Evidence:** editor.js:655, editor.js:912; extra-crew.js, crewEquipmentChoices; mission.js:8, missionConfigurationIssues. Save validation catches some missing references, so this review does not claim every deletion can produce a distributed broken configuration.

**Next stage:** Understand with a dependency map and reproduce candidate cases. Explore dependency-aware rejection, explicit replacement/relocation, and retirement before deciding the scope. Account for live drafts as well as persisted saves.

**Acceptance:** Exercise referenced carrier deletion, extra-crew bag retirement/replacement, recorded-fit deletion and inactive saved allocations. Each operation either preserves valid accounting or explains the dependency and recovery action; no silent loss of an accepted contribution. Verify reversal, reload, certification and PDF effects.

## 4. Stowage capacity ownership — high priority for data changes

**Classification:** confirmed design boundary needing an explicit custodian policy (PRO-04/07/12).

**Problem:** Location names and arms are editable configuration data, while capacities remain in STOW_MAX in app.js. A new Editor location does not acquire a capacity check simply by being created. This can be misunderstood as a complete location-definition capability.

**Evidence:** app.js:1648; editor.js:763; extra-crew.js:94 explicitly warns when no capacity is defined.

**Next stage:** Decide whether capacities remain maintained by the software maintainer with clear instructions, or become validated configuration fields. Do not infer that every location needs a shelf limit or that undefined means unlimited.

**Acceptance:** Each relevant load-bearing location has a source-backed limit or explicit unverified/not-applicable disposition. Custodians can identify what is checked. Mission equipment and loose cargo share the intended limit calculation, including at-limit and just-over-limit cases.

## 5. Editor validation and live-change behaviour — high priority verification

**Classification:** validation/state-transition verification (PRO-07/08/10).

**Problem:** Editor saves immediately replace live data and invalidate certification. The visible catalogue validator checks mission numerical values and reference membership, but does not itself establish comprehensive numerical validation for every role-fit and seat field, or every carrier cycle. UI constraints and downstream checks may cover some cases; their coverage needs mapping.

**Evidence:** editor.js:91–148; mission.js:17–37. Mission location resolution already has runtime cycle/unavailable-carrier handling; preserve it.

**Next stage:** Inventory validation at entry, save, export, restore, computation and certification. Reproduce blanks, malformed/non-finite values, intentional negative adjustments, indirect cycles and catalogue changes during accepted sessions before classifying bugs.

**Acceptance:** Invalid data cannot become plausible certified output; errors explain correction. A rejected save cannot leave confusing live draft state. Normal → edge → reversal → persistence → interaction cases cover each consequential field and dependency.

## 6. Release identity, overrides and recovery — high priority assurance

**Classification:** release-process requirement and verification (PRO-06/09/10/11).

**Problem:** App/configuration version labels are useful but do not uniquely identify all browser-local data. The mission signature covers selected datasets; Editor changes, exported revisions, accepted snapshots and restored releases must remain interpretable as a whole. Existing recovery mechanisms are strengths to verify, not presumed defects.

**Evidence:** mission.js:85; editor.js:990; persist.js restore/reset paths; app.js offline status handling; existing register PRO-06 and PRO-09/10.

**Next stage:** Trace one candidate through local edit → export → distribution → online update → offline reopen → rollback. Decide the minimum provenance record needed to identify the exact data behind a PDF.

**Acceptance:** Record candidate identity, effective data and local-change status, test environment and rollback compatibility. Exercise storage-full, damaged-save, interrupted-update and stale-override cases. Check that downstream changes require the correct revalidation and that app/PDF results agree.

## 7. Operational device and FE trials — before operational release

**Classification:** verification requirement, not a demonstrated usability bug (PRO-05/13).

**Problem:** Desktop browser tests at tablet dimensions do not establish physical iPad/Safari, touch, installation, download and offline workflow suitability. Existing notes explicitly leave physical-device/operator acceptance outstanding.

**Next stage:** Run realistic FE scenarios on an identified candidate and intended devices. Include partial equipment fit, patients, crew in passenger seats, corrections, MCDU mismatch, interruption and offline recovery.

**Acceptance:** Record user interpretation as well as completion. Confirm critical values/actions remain readable and reachable, mistakes have understandable recovery, and findings are reproduced and retested. Separate operational trials from aircraft-source validation.

## 8. Manuals and obsolete development descriptions — before documentation freeze

**Classification:** documentation requirement and confirmed stale descriptions (PRO-12).

**Problem:** Comprehensive User and Editor instructions are planned, not delivered. Older documents describe a complete combined rack installation and historical tab/update behaviour, while current config and manual checklist describe independent racks. Some code comments also describe older stowage structures. A successor could follow the wrong description.

**Evidence:** handover data constraints versus config.js:908 onward and the latest manual checklist; MISSION_REVISION_REVIEW.md is explicitly identified as historical; editor.js stowage-section comment. The independent-rack decision and negligible complete-set moment difference are already recorded; do not reopen them merely to align text.

**Next stage:** Label superseded descriptions and establish which release-specific document is authoritative. Prepare distinct self-contained User and Editor parts, with shared technical references and version-matched procedures.

**Acceptance:** A first-time operator and successor custodian can complete representative procedures using the manuals; every instruction matches the frozen release. Editor coverage includes field meaning, dependencies, local save versus distribution, validation and recovery.

## Conditional/later work

- **Central publication authorization (PRO-14):** The current client-side password is a local workflow barrier. Stronger publication controls become a priority if the deployment relies on centralized authorized fleet publication. Document the current trust model; do not start an identity-platform redesign solely for local editing.
- **Focused cleanup (PRO-15):** Recheck supposedly unused helpers and obsolete comments after the behavioural baseline is dependable. Preserve migration support, exact calculation precision and centralized envelope logic. Module size alone does not justify a broad refactor.

## Recommended sequence

1. Make verification reproducible and identify the current candidate.
2. Establish source/independent-calculation evidence in parallel with reproducing Editor dependency and validation cases as ordinary project activities.
3. Resolve confirmed integrity findings with small scoped changes and explicit acceptance criteria.
4. Exercise release, persistence, output and offline recovery on that candidate.
5. Run FE/device trials, then freeze matching User and Editor instructions.

No new Mission Equipment visit/confirmation gate is proposed. No settled basic-weight accounting or rack decision is reopened without contrary evidence. Record newly reproduced failures separately from broader design choices, and update the improvement register with their evidence and disposition.
